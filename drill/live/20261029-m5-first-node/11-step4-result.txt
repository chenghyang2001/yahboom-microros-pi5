第四步的結果，四件事都照預期發生。

第一，scan timeout 改成一點零，第三格回應 Set parameter successful。改完以後，第二格之前每隔幾十秒就跳一次的黃色警告就沒有再出現了。

第二，stop distance 改成零點二，也是 successful。第二格馬上印「前方淨空零點二八公尺，繼續前進」，大約三秒後印「前方零點一八公尺有障礙，停車」。odom 的 x 從一點一四六變成一點二六六，車子又往前走了十二公分。整個過程程式一行都沒改，也沒有重新編譯，這就是把數字做成參數的好處。順便注意，停下的位置是零點一八，比設定的零點二稍微近一點，因為節點每零點一秒才判斷一次，加上模擬的光達資料有延遲，車子會多滑一點點。真車上也會有同樣的現象。

第三，在第一格按 Ctrl C 關掉模擬車。Gazebo 五秒內沒有自己結束，launch 只好改送 SIGTERM 強制關掉，所以第一格印了幾行 ERROR，這是 Gazebo 本身關得慢，不影響我們。重點在第二格：光達一斷，節點連續印出「超過一點零秒、三點零秒、四點八秒、七點四秒沒收到 scan，先停車」。數字一直變大，代表節點一直在送零速度，不會帶著最後的速度往前衝。警告每兩秒才印一次，是程式裡設定的節流，避免洗版。

第四，在第二格按 Ctrl C 結束節點，直接回到提示字元，沒有任何錯誤訊息，表示結束前送零速度的那段程式正常運作。

前半場的模擬車測試到這裡結束。下一步要搬到真車：先在第三格把套件打包成壓縮檔，用 scp 傳到 Pi 5，然後畫面切換到 Pi 的 VNC 桌面，在車上解壓縮、複製進 Docker 容器。等你說繼續。
